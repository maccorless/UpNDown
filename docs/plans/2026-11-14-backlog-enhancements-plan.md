## 2. Ground rules that apply to every item

These come from the project and global instructions and from decisions Ken has already made. Every item is checked against them.

1. **Before each commit:** `npm run test`, `npm run typecheck` and lint pass; the client version in `apps/client/src/version.ts` goes up by 0.01; a row goes into `docs/toshare/changelog.md`; `GAME_MECHANICS.md` and `requirements.md` are updated in the same commit whenever a rule, setting, socket event or limit changes.
2. **Solitaire works with no connection** (decision of 14-Nov-2026). It may touch the server only to sign in and to save a signed-in player's finished game. So hints, cheats and any solitaire feature in this plan must run in the client with `fetch` rejecting. The tests that count requests during solitaire (`App.solitaire-result.test.tsx`) must keep passing.
3. **The server is authoritative.** In multiplayer, every state change goes through `packages/engine` and is applied by `apps/server`. The client never decides a rule. Hidden information (other players' hands, the draw pile) never leaves the server; `apps/server/src/player-view.ts` replaces it with placeholders.
4. **Saved data stays readable.** A solitaire game saved in a browser before a change must still load after it. New fields in `gameStateSchema` are optional with a default, or the save is migrated. Stored result rows follow the same rule with migrations.
5. **`App.tsx` does not grow** (it is about 2,500 lines and is documented tech debt). New client behavior goes in new components and hooks. The planned `App.tsx` split (`APP_DECOMPOSITION_PLAN.md`) is not a prerequisite for this plan but would make workstreams B and E easier; see section 5.
6. **Accessibility:** every new control has a keyboard path and an accessible name; anything revealed by a gesture (double tap, hotkey) also has a visible, focusable alternative.
7. **No em-dashes** in documents, per the global instructions.

## 3. Workstreams

### A. Quick wins

**A1. Center the arrows on the foundation piles (S).**
Current state: `.pile-arrow` sits in a flex row with `gap: 4px` on each side of the top card (`apps/client/src/App.css`, around line 509 to 535), so the arrows hug the card. Design: let the two arrows spread so each sits in the middle of the free space on its side of the card (for example `justify-content: space-around` on the row, with the card's width held fixed), and keep the narrow-phone rules (`@media` blocks near lines 1305 and 1337) so the card and both arrows still fit at 360 px. Tests: the existing smoke and accessibility specs, plus a screenshot check at 360, 768 and 1280 px in both themes. Risk: low, CSS only.

**A2. Up to 11 cards in a hand (S).**
Current state: `HAND_MAX = 9` and `HAND_MIN = 5` in `packages/shared-types/src/schemas.ts`; the default is 7. The settings schema checks the deck is at least `MIN_DECK_SIZE` but does not check that `players x handSize` fits in the deck. The deck (`buildDeck`) holds every card in the range; the four foundation piles are created separately (`createFoundationPiles`), so they do not come out of it. The deal is in `createStartedGameState` in `transitions.ts`. Design: raise `HAND_MAX` to 11; add a check at game start (in the engine) that `players x handSize` is at most the number of cards in the deck, with a clear message, and refuse settings that cannot be dealt at the maximum player count, in the Settings dialog and on the server when settings are created or updated (decision 11, decided: checked against the deck size in both places). The schema itself is not tightened for existing data: `gameSettingsSchema` also validates saved solitaire games and their undo snapshots, and a save that fails validation is deleted (`solitaire-save.ts`), so a stricter schema could destroy saved games; update the Settings stepper range; make the hand panel wrap or scale at 11 cards on a 360 px phone; update the constants table in the project guide, `GAME_MECHANICS.md` and `requirements.md` (hand size 5 to 11). With the default 2 to 99 range (98 cards) 6 players x 11 cards is 66, so the default deck is fine; the check matters for small custom decks. Tests: schema accepts 11 and rejects 12; start refuses an undealable table; a hand of 11 renders without horizontal scroll at 360 px; a saved game with a hand of 9 still loads. Risk: layout on narrow screens.

### B. Cheats

Current state, from the code: there is already a "Nas Cheat" (a card swap, once per turn, enabled only for a player whose name is "nas": `useNasCheat` in `packages/engine/src/transitions.ts`, `nasCheat` state in `packages/shared-types/src/game-types.ts`, the `game:nasCheat` event, a stats counter `nasCheatsUsed`, a column `my_nas_cheats` in the results table). The card seeker (card lookup) is enabled by the setting `allowCardLookup`, opened with ctrl-shift-C (`apps/client/src/App.tsx`, around line 1074), and works two ways (`game:cardLookup` in `apps/server/src/index.ts`): an ordinary lookup broadcasts its result, including where the card is, to everyone in the room, and a lookup flagged `secret` (the Shift submit) is answered in the asker's ack only. So today other players already see ordinary lookups and never see secret ones. The new work generalizes this into a small family of cheats.

**Cheat model (shared by B1 to B6).** A cheat is one of `lookup`, `skip`, `trade` (and `hint`, D1). Each has a per-game limit setting with three values (decided 15-Nov-2026): **off**, **once** (one use per player per game) or **unlimited**. The existing boolean `allowCardLookup` stays readable for saved games and settings and maps to unlimited (true) or off (false); the new settings are an optional `cheatLimits` object (`lookup`, `skip`, `trade`, `hint`) that defaults to off, except that `lookup` defaults from `allowCardLookup`. Cheat actions that change the game (`skip`, `trade`) are never undoable and never refund usage; see the shared undo policy under B4. Neither is a loss rescue (decision 2). Each cheat has a per-player usage count in `statistics.players[id]`, counted whatever the limit.

**Counting "once" budgets.** Counters live in `statistics.players[id]`, which follows a seat across a rejoin (`swapPlayerId`) but vanishes when a seat is removed; a player who leaves and is re-admitted through E1 would get a fresh budget. So once-budgets are also recorded in the room by account (signed in) or by rejoin token (guest) and kept for the whole game, and a re-admitted seat inherits what that account already used.

**B1. Cheats panel, gray-out, notifications (M).**
Design: a double tap (and double click) on the UpNDown logo opens a small panel listing the cheats the game allows, each a button. A cheat the player has used up under the "once" limit is grayed out and disabled (an unlimited cheat never is) (`aria-disabled` plus a visible "used" label, not color alone). In multiplayer the server pushes a `game:cheatUsed` event, `{ playerId, kind }`, to everyone in the room and every client shows a short toast ("Ann used Skip"); in solitaire nothing is shown to anyone. The panel is a new component (not in `App.tsx`). Accessibility: a double tap is a hidden gesture, so the panel also opens from a focusable "Cheats" entry in the game menu when at least one cheat is allowed (this is also what a screen reader and keyboard user will use). Tests: panel opens on double tap and from the menu; used cheats are disabled; the server event reaches the other players and not solitaire; the toast is announced politely (not `role="status"`, which the end-to-end specs select strictly).

**B2. Cheat code section in Settings (S).**
Design: a "Cheat codes" group in the Settings dialog with a three-way choice per cheat (off, once, unlimited) for the card seeker, skip, trade and hint. For multiplayer it sits in the host's game settings (view-only for others, as other settings are); for solitaire it sits in the solitaire settings. Defaults: all off for multiplayer, as `allowCardLookup` is today. Settings are validated by `gameSettingsSchema` (shared types) so `cheatLimits` is added there as optional with a default of off, so saved settings and saved solitaire games still parse. Precedence: when `cheatLimits.lookup` is present it wins; the server writes both fields during one release (`allowCardLookup` is true whenever the lookup limit is not off), so the old container during a deploy still reads a valid setting. The server gate (`settings.allowCardLookup`, `game-manager.ts` line 862) and the client hotkey switch to the new setting in the same commit. Tests: schema defaults and the `allowCardLookup` mapping; the dialog shows the group; changing a limit persists for signed-in players through the existing settings sync.

**B3. Skip (M).**
Rule (decided 15-Nov-2026): skip is limited per the skip setting (once per player per game, or unlimited) and used proactively. On your turn you may pass without meeting the minimum plays; your turn ends and play moves to the next player. It does not refill your hand. A skip is not a rescue: the engine declares a loss the moment the active player has no legal play and has not met the minimum (`evaluateLossForCurrentPlayer`, run at the end of `playCard` and `endTurn`), so once a player is stuck the game is over and Skip is no longer possible. That keeps the core loss rule unchanged. The Skip button is only offered during the player's own turn while the game is `playing`; the hint function (D1) can warn that a play would leave the player stuck, which is when skipping first is useful. Design: engine function `skipTurn(state, playerId)` in `transitions.ts` that checks phase, turn, setting and remaining skips, advances the turn exactly as `endTurn` does apart from the minimum check, bumps the counter, and re-evaluates win and loss for the next player. Server: a `game:skip` event with the usual rate limit, schema validation and ack, and the `game:cheatUsed` push. Client: the panel button and the hotkey, behind an "are you sure?" confirmation dialog (the existing `Modal`). Solitaire has no turn to skip, so Skip is not offered there. Two holes the second review found: (1) with the unlimited setting, a table could skip forever, since a win needs cards played and a loss needs a stuck player; so a full round of skips with no card played by anyone ends the game as a loss (decision 14). (2) a skip after one card was played, with refill off, would leave the hand untopped (the draw happens only in `endTurn`), so Skip is only offered while no card has been played this turn. Tests: cannot skip off turn, twice, when disabled, or when the game is over; the turn advances and the next player is evaluated (and can lose, as normal); undo interaction (see the shared undo policy under B4).

**B4. Trade (M).**
Rule as written: a card from the hand is swapped for the next card in the draw pile, limited per the trade setting (once per player per game, or unlimited). This is the existing Nas swap generalized (see decision 1). Design: reuse the engine's swap logic (rename to `tradeCard`), drop the "once per turn" and name-gating rules in favor of the per-game limit setting, and keep the requirement that the draw pile is not empty. The card taken from the hand is put back into the draw pile at a random position (decided 15-Nov-2026), so nobody can tell where it went; the limit is the trade setting (once or unlimited). The engine stays pure: the random position is chosen by the caller and passed in the action (the server, or the solitaire client), and for solitaire the chosen position is stored in the undo snapshot so undo and reload never re-roll it. Trade keeps the existing Nas rule that only the active player may use it, and win and loss are re-evaluated after it. Server: `game:trade` (replacing `game:nasCheat`) plus the push. Tests: swap is exact (card ids conserved, hand size unchanged, draw pile length unchanged); not with an empty draw pile; the limit setting is enforced (off, once, unlimited); the returned card lands at a random position; solitaire works offline. Migration of old behavior: players named "nas" no longer get a special mode. Note that today's swap (`GameManager.nasCheat`) does not clear the undo stack, so play, swap, undo already restores an earlier state and refunds the swap.

**Undo policy for B3, B4 and E1 (shared).** Undo restores a whole earlier state, so any action that is not a card play would be silently reversed or have its cost refunded (play, trade, undo gives the trade back and the old card; play, admit a newcomer, undo erases the newcomer). Rule: skip, trade and admission clear the undo stack (they are barriers), lookup and hint accounting live outside the snapshots, and the saved solitaire undo history follows the same rule. Tests: after each of these actions, undo is refused for anything before it.

**B5. Use of cheats in the final and in history (M).**
Design: `PlayerStatistics` gains `skipsUsed`, `tradesUsed`, `lookupsUsed` (replacing `nasCheatsUsed`, which is kept readable for old saves and mapped to `tradesUsed`). The end-of-game statistics modal and splash list each player's cheats. Stored results: a migration (`003_cheats_in_results`) adds `my_skips`, `my_trades`, `my_lookups` (integers, default 0) and keeps `my_nas_cheats`. Existing rows keep their Nas count there; the history API reads `my_trades + my_nas_cheats` as trades so old games are not shown as zero, and new rows write 0 to `my_nas_cheats`. Because the old container keeps serving during a deploy (the migration comment in `migrations.ts` says so), rows written by it during rollout still use `my_nas_cheats`, which the same read rule covers. A legacy solitaire save with a nonzero `nasCheatsUsed` converts to `tradesUsed` with that value, not zero. `buildResultRows`, `buildSolitaireRow`, `solitaireResultSchema`, the profile history API and the history page (when it exists) follow. The solitaire payload schema is strict and checked against settings, so the new fields are added there as optional with a default of 0. Tests: counters increment exactly once per use; they survive a rejoin (`swapPlayerId` moves statistics) and a kick; they appear in the modal and in the stored rows; an old saved solitaire game loads with its old count carried over, and zeros where there was none. Risk: the stored-results schema is permanent; get the column names right before shipping.

**B6. Card seeker hotkey to ctrl/cmd-P (S).**
Design: replace the ctrl-shift-C handler with ctrl/cmd-P (using `event.code === 'KeyP'` and `ctrlKey || metaKey`, with `preventDefault()`), active only while a game is being played and the cheat is allowed, so printing still works everywhere else. Risk: ctrl/cmd-P is the browser's print shortcut; pages can usually intercept it but it is fragile (and a user who wants to print mid-game loses it). 

**Hotkeys.** Card seeker: ctrl/cmd-P. Skip: ctrl/cmd-S (save page, can be intercepted). Trade: decided 15-Nov-2026 to use a different hotkey than the backlog's ctrl-T. ctrl/cmd-E is not suitable (it focuses the address bar or searches the selection in Chrome, Firefox and Safari), and neither is ctrl/cmd-S on a shaky basis, so the key is chosen at build time from candidates that survive the per-browser test below; skip keeps ctrl/cmd-S as requested only if it passes the same test. Hotkeys are ignored while a text field (including the card seeker's input) has focus. ctrl/cmd-T opens a new tab and cannot be intercepted by a web page in Chrome, Safari or Firefox, so it cannot be used. Before shipping, each hotkey is tried in Chrome, Safari and Firefox on Mac and Windows to confirm `preventDefault()` works there; any that does not is dropped, since hotkeys are accelerators only. The panel buttons are the primary path and work on touch devices, which have no keyboard.

### C. Persistence and picking up an in-flight game after sign-in

**C1. Game state in the database (L).**
Current state: rooms live only in `GameManager` memory; a restart or deploy ends every game (documented v1 limitation). A signed-in player can already take a held seat back by account while the server is up (`game:rejoinMine`, `GameManager.rejoinByAccount`), and a guest by the saved seat token. What is missing is surviving a restart, which is also what the privacy page says is planned.

Design:
- A `GameStore` interface (like the existing `ProfileStore`) with a memory implementation (used by Skiff, which has no database, and by tests) and a Postgres implementation. Migration `004_live_games`: table `live_games(game_id text primary key, state jsonb, seat_users jsonb, token_hashes jsonb, run_id text, disconnected jsonb, version int, updated_at timestamptz)`.
- One writer at a time. Railway's own documentation says a new deployment is started and then the old one is stopped, the old one gets a configurable drain time (`RAILWAY_DEPLOYMENT_DRAINING_SECONDS`) after `SIGTERM`, and `RAILWAY_DEPLOYMENT_OVERLAP_SECONDS` (default 0) can keep it longer. Checked 15-Nov-2026: neither variable is set on this service, so defaults apply; the Railway forum has a staff-acknowledged report that a few seconds of overlap remain even with overlap set to 0, unfixed. So stop-before-start cannot be configured and the plan does not rely on it. The plan uses a Postgres session-level advisory lock, hardened after the second review: the lock is held on its own dedicated, non-pooled `pg.Client` (the shared pool in `auth/runtime.ts` has `max: 3` and may drop idle clients, which would silently release a lock held on one of them), with its own reconnect and a "lock lost" callback that makes the process stop writing at once. Acquisition polls `pg_try_advisory_lock` with a timeout instead of blocking forever, so a wedged holder cannot hang a new process. The lock key differs from the migration runner's (`MIGRATION_LOCK_KEY` 7_265_001, `db/migrate.ts`). The lock is a courtesy; correctness comes from a compare-and-set on `live_games.version` (`update ... where version = $n`), so a stale writer cannot overwrite a newer state whatever the lock does. The new process serves play from memory while it waits; rooms created in that time are written once the lock is acquired. The lock is exact only among processes of the version that takes it: the first deploy of C1 overlaps an old container that never writes `live_games`, which is harmless. It is recommended that `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` be set (for example 15) so the old process can flush its last writes; this is a Railway setting and this plan does not change it.
- Write-through after each accepted transition, best effort for latency (a write never blocks a move) but not for ordering: writes for a room are serialized and carry a revision number, a write for an older revision is dropped, and deleting a room sets a barrier so a pending write cannot bring a deleted room back. A debounce coalesces bursts to at most a few writes a second per room, so a crash can lose the last moments of play; that is accepted and bounded by the debounce window. A rotated guest credential is the exception: when a seat is reseated (new socket id, new token hash) that write is awaited before the new token is given to the client, so a restart can never leave a player holding a token the database has not seen. The finished-game state and the result rows are written together so a restart cannot show a game as in progress after its result was recorded. Skiff has no database by design: there the storage status says "none", the same friendly notice is shown (decided 15-Nov-2026), and games run from memory as today. A database outage on Railway means games run from memory exactly as today and are not recoverable until it returns; the player sees a friendly message (decision 12, decided): a banner on the home page and in the game saying that saving is unavailable and that games may be lost if the server restarts, and sign-in is shown as unavailable with the same wording. This needs a storage status the client can read (a field on the existing `/auth/me` response and on `server:ready`), and it clears itself when the database returns. Today it could not: `auth/runtime.ts` connects once at startup, and on failure logs `auth.disabled`, closes the pool and never retries, so a boot while the database is down leaves auth, saving and the lock off until the next restart. C1 adds a reconnect loop so the status can go from down to ok without a restart. Solitaire is never affected.
- On startup, load rooms whose `updated_at` is recent; every seat starts as disconnected, so the dropped-connection rules (10 s notice, 90 s kick) apply and the existing rejoin paths work: signed-in players by account, guests by token.
- Rejoin tokens are stored as hashes, and `rejoinPlayer` compares hashes. The player id is a socket id and changes on reconnect, so stored ids are replaced as players rejoin.
- Rooms are deleted when the game ends, when everyone leaves, and by the reaper: once state is durable the limit is 24 hours with nobody connected (decided 15-Nov-2026; today it is 30 minutes in memory).
- The stored blob carries a `version`; a load of an unknown version drops the room rather than guessing. This is why C1 follows the cheat work: state shape should settle first.
- Hidden hands are stored server-side in the database. They are only readable by the operator, and the privacy page was updated on 15-Nov-2026 to describe this (what is kept, for how long, and that it is deleted when the game ends), and its wording is checked again when C1 ships.
- Sign-in UI: after a restart, a signed-in player who opens Multiplayer is put back by account (already built). The new part is a "your games" prompt when the account holds more than one game, which is also the remaining gap in the multi-tab work (the account rejoin picks the first held seat). That needs a `game:mySeats` listing and a choice.

Tests: store contract tests run against both stores (as `profile-store.contract.test.ts` does); a restart test that creates a game, stops the server, starts a new one on the same database, and has both a guest (token) and an account rejoin; debounce and failure behavior; unknown version dropped; the throwaway Postgres harness in `fullcheck.sh` already exists. Risks: write volume on busy games; overlap during a deploy: the migration comment says the old container keeps serving while the new one starts, so two processes can both load and write a room. "Single instance" is therefore not enough. The advisory lock described above fixes this. Timers (disconnect notices, robot turns) must be rebuilt on load.

### D. Hints, robots, learning

**D1. Hint function (L).**
Design: a pure function in the engine, `suggestPlays(state, playerId): Suggestion[]`, ranked, using only what the player can see (their own hand, the foundation piles, the size of the draw pile). It runs in the client for solitaire (offline) and for multiplayer (the client already has its own hand), so it needs no server call and leaks nothing. Information boundary: the engine's existing look-ahead (`canPlayerSatisfyRequiredPlays`) consumes the real draw cards when auto-refill is on, but a multiplayer client only holds placeholder cards of value 0 for the draw pile (`player-view.ts`). Reusing it as is would make client hints reason about cards that do not exist and would let a server robot use cards it should not know. So the strategy takes an explicit `Observation` (own hand, pile tops, draw pile size, other hands' sizes) and treats future draws as unknown; the look-ahead is rewritten to branch on "some unseen card" instead of a real one. A test feeds two states that differ only in hidden cards and requires identical recommendations. Strategy, in order of weight:
1. Prefer plays that move a pile the least (small gaps keep the piles useful for everyone), measured against the other cards in hand.
2. Prefer the backward ten when it is available and safe, since it undoes ten points of progress for free.
3. Avoid plays that strand a card, meaning a hand card that no pile can ever accept again.
4. Respect the turn's minimum: if plays remain to be made this turn, pick a set of plays that keeps a legal continuation (the engine already has a depth-first check, `canPlayerSatisfyRequiredPlays`, which the strategy reuses).
5. In multiplayer, avoid playing to a pile a teammate's visible reaction marks as theirs (reactions already exist).
The first version is heuristic with a short lookahead; the weights live in one table so D3 can tune them. A simulation harness plays thousands of seeded solitaire games with the strategy and reports win rate and cards left, which is how "intelligent" is measured and how regressions are caught. UI: a Hint button (and a key) that highlights the suggested card and pile; it appears only when a new game setting `allowHints` is on (treated as a cheat for statistics: `hintsUsed` joins the counters in B5 if Ken wants it counted, see section 6). Tests: a table of hand-built positions with a known best play; the harness asserts a minimum win rate so the strategy cannot silently get worse; the hint never suggests an illegal play (property test against `isValidPlay`); solitaire hint works with `fetch` rejecting.

**D2. Robot player in multiplayer (L).**
Design: a seat flagged `robot: true` in the game state. The host adds or removes robots in the lobby (a robot counts toward `minPlayers` and `maxPlayers`, decided 15-Nov-2026, with no cap other than `maxPlayers`; at least one human must be seated). Robots must be excluded from the dropped-connection logic: `nextAvailablePlayerId` treats a seat with no disconnect record as connected, so a robot in the next seat after a lost host would be offered the host's seat and no human could ever take over; host succession and the take-over rule skip robot seats. When the last human is gone (dropped and kicked, or left) the robots pause and the game ends as abandoned after the same 90 seconds, rather than robots playing on unwatched until the 24 hour reaper (the reaper counts sockets, so a robots-only room would otherwise survive that long). The server drives robot turns: when it becomes a robot's turn, a timer (a short, human-feeling delay, for example 1 to 2 seconds per play) calls the same strategy through the same `Observation` as a human hint (so a robot cannot see hidden cards) and applies its choices through `GameManager`. The strategy returns an action, not only a card: play, end turn, skip or trade, because multiplayer needs an explicit `endTurn` after the minimum is met (that is when refill and the turn advance happen), and a robot that only plays cards would stall. Timer callbacks carry the run id and turn number they were scheduled for and do nothing if either has changed. so every rule check is shared and a robot cannot cheat. Robots never disconnect, are never kicked by the dropped-connection rules, have no account, and are not recorded in results (a game's `playerCount` still counts them). The turn driver must be idempotent and safe if a human acts at the same moment (server turn lock), and must be rebuilt after a restart (C1), which is why C1 is preferred first. Tests: a table of one human and robots finishes a game; a robot never plays out of turn or illegally; robot timers stop when the room is deleted; results are recorded for the human only.

**D3. All-robot learning runs, local only (L, optional).**
Design: a command-line tool in a new workspace (`tools/sim`), never part of the server or client bundle. It runs all-robot games with the engine and tunes the hint weights. The reward is the one in the backlog: a win scores the maximum, a loss scores by fewer cards remaining. Recommendation: start with random search and hill climbing over the weight table (cheap, explainable, reproducible) before any reinforcement learning; the game is cooperative, so one policy plays every seat, which keeps the problem single-agent. Move to a learned policy (for example policy-gradient or a value network) only if the weight search plateaus below an acceptable win rate. Output: a weights JSON file that D1 loads, committed with the run's seed, win rate and date. It is local only because it is a development tool and uses no player data.

### E. Join an in-flight game by invitation

**E1. Late join with host approval (L).**
Rule as written: a new player may join a game in flight if specifically invited; the host confirms; the player is dealt in from the draw pile; other hands and the piles do not change.
Design:
- A host setting `allowLateJoin` and a host action "Invite to this game" that creates a single-use invite (an unguessable token in a link, expiring after a short time).
- The invitee opens the link, enters a name, and sends `game:requestJoin { gameId, inviteToken, playerName }`. The server validates the token, then holds the request and pushes `game:joinRequest` to the host only. The host sees "Ann wants to join. Let in?" and answers with `game:resolveJoin`. The request expires if unanswered.
- On approval the server adds the player at the end of the seat order, deals `handSize` cards from the draw pile (or as many as remain), leaves every other hand and every pile unchanged, adds a statistics entry, records the account for a signed-in player (one seat per account still applies), and broadcasts. If the draw pile cannot give at least one card, the join is refused with a clear message (a player dealt nothing adds nothing to the game).
- Approval is an atomic commit: when the host approves, the server re-checks host authority, that the game is still `playing`, capacity, that the account does not already hold a seat, that the invite is unexpired and unused, and that the draw pile still has cards. Anything that changed since the request (plays, disconnects, another admission, the game ending) is re-evaluated, not assumed. Dealing from the draw pile also changes the active turn's required minimum at once (`requiredCardsForTurn` depends on the draw pile size in `rules.ts`), so, by decision 13 (15-Nov-2026), admission is allowed at any time while the game is `playing`. The minimum only ever drops when the pile empties (`requiredCardsForTurn` returns 1 for an empty draw pile), which helps the active player, so it needs no special handling. The one real hazard is the active player's own refills: dealing the newcomer from the top of the draw pile could take the card the active player would have drawn next and leave them stuck. So the newcomer is dealt from the bottom of the draw pile (refills draw from the top, and the pile is already shuffled, so no one can tell the difference), and the admission is refused (with a message to try again after the next play) if the state after dealing would be `lost`: the loss check looks ahead through real draw cards, so removing even bottom cards can change its answer, and an admission must never be what ends a game. The same check refuses a deal that leaves too few cards for the active player's turn. Admission is an undo barrier (see the shared undo policy).
- Rate limits and schema validation apply to both new events; the request and invite tables are in memory and bounded, and are persisted with the room once C1 exists.
Tests: approval deals exactly the right number of cards and changes nothing else (every other hand and pile equal before and after); refusal and expiry leave the game untouched; an invite works once; the cap `maxPlayers` is respected; a late joiner's result is recorded with their own counts; hidden hands stay hidden in the broadcast. Risks: fairness (a robot-like late joiner changes difficulty mid-game, which the host accepts by confirming); the lobby's join-by-code path must stay closed once a game has started (it is today: `joinGame` throws unless the phase is lobby).

### F. How to Play

### G. Training mode (future phase, not scheduled)

Decided 15-Nov-2026: robots must be able to play unwatched in a training mode that feeds the learning runs (D3), someone must be able to start it and watch the outcomes, and the whole mode gets its own design before any build. It is held for a later phase. This plan only makes sure nothing built now blocks it.

What the later design has to answer (questions, not decisions):
- **Where it runs.** The original backlog says local only. Local means a command or a small local app on the developer's machine using the engine directly: no server, no accounts, no player data, no load on the game server. Running it on the production server would need an admin gate, a CPU and time budget so training cannot slow real games, and a decision about whether its games touch the results tables (they must not).
- **How someone starts it and watches.** A command to start a run (games, seeds, strategy weights, reward settings) and a viewer for the outcomes: win rate and average cards left over time, the best weights so far, and a replay of a chosen game from its seed. A local page that reads the run's result files is the lightest option and needs no server.
- **How it differs from D2.** D2 robots sit at a table with humans and obey the rules for human tables (pause and abandon when no human remains). Training games have no humans by design, are never persisted or recorded for any account, run as fast as possible with no pacing delays, and are driven in process, not through sockets.
- **What it needs from the work already planned.** A headless strategy that sees only an observation (D1), a deterministic engine with injected randomness so a seed reproduces a game (B4 already moves random choices out of the engine), and the weights file format (D3).
- **Open design questions for that phase:** reward shaping beyond win and cards left, reproducibility and versioning of strategies, how a trained strategy is promoted into the shipped hint and robot, and whether a human can play against a candidate strategy before it ships.

Nothing in A to F depends on G, and G should not start until D1 to D3 exist.

## 5. Risks across the plan

- **`App.tsx` size.** B, D1 and E1 all add UI. If each is built as a component and a hook, `App.tsx` grows by a few lines apiece. If not, the planned decomposition becomes urgent. Recommendation: do the first safe move of the decomposition (extract `GameBoard`) before B1.
- **Stored schema is forever.** B5 and C1 add columns and a table. Name them carefully and review the migration before shipping.
- **Browser shortcuts.** ctrl/cmd-T cannot be intercepted; ctrl/cmd-P and ctrl/cmd-S can but may annoy. The panel is the real interface.
- **Hint and robot quality.** A weak strategy is worse than none. The harness's minimum win rate is the guard, and it should be agreed before D2 ships.
- **Deploy overlap.** The old container keeps serving during a deploy and Railway cannot be set to stop it first. C1 uses a Postgres advisory lock so only one process loads and writes rooms.
- **Offline solitaire.** Every new solitaire feature is tested with `fetch` rejecting.
